# Monte Carlo Path Tracing from Scratch

## 1. Problem

We want to render a photorealistic image of a 3D scene: for every pixel, compute
how much light arrives at the camera through that pixel.

Light leaves a light source, bounces between surfaces (each bounce absorbs part of
it and scatters the rest in some direction), and some of it finally reaches the
camera. The color of a pixel is therefore an integral over *all possible light
paths* from the light to the camera through that pixel (the "rendering equation").
This integral has no closed form for any interesting scene.

**Monte Carlo path tracing** estimates it by random sampling. From the camera we
shoot a ray through a random point inside the pixel, follow it as it bounces in
random directions chosen according to each surface's material, and record the
light it picks up. Averaging many such random paths (samples per pixel, *spp*)
converges to the correct image. The error (visible as noise) decreases as
1/sqrt(spp): 4x more samples halve the noise.

This produces effects that are hard to get otherwise: soft shadows, color bleeding
(a red wall tints the white floor next to it), reflections, refraction through
glass and caustics (light focused by a glass ball onto the floor).

## 2. Scenes

All geometry is generated by the program; there are no input files.

- **Scene 0: Cornell box with analytic spheres.** A box with a red left wall, a
  green right wall, white floor/ceiling/back wall and a square area light on the
  ceiling. Inside: a diffuse (matte) sphere, a mirror sphere and a glass sphere.
  The Cornell box is a standard test scene in graphics, so the expected look is
  well known.
- **Scene 1: the same box, but the three spheres are triangle meshes**
  (icospheres: an icosahedron whose triangles are split into 4 recursively, so
  each object has 20 * 4^D triangles). D controls the amount of geometry; this is
  the main workload.
- **Scene 2: furnace test.** A pure white (albedo 1) diffuse sphere made of
  triangles inside a uniform white environment. Physically, no energy is lost, so
  every pixel must be exactly 1.

## 3. Baseline code

About 800 lines of C++17, no external libraries, single-threaded.

| file | role |
|---|---|
| vec3.h | 3D vector (points, directions, RGB colors) |
| rng.h | random number generator (xorshift64*), seeded from (pixel, sample) |
| geometry.h/.cc | ray, triangle, sphere, axis-aligned bounding box; ray-triangle (Moller-Trumbore), ray-sphere and ray-box (slab) intersection |
| bvh.h/.cc | bounding volume hierarchy: build and traversal |
| material.h/.cc | sampling the bounce direction for diffuse, mirror and glass surfaces |
| scene.h/.cc | camera and procedural scenes (Cornell box, icosphere meshes, furnace) |
| render.h/.cc | the path tracing loop |
| image.h/.cc | PPM/PFM output, verification metrics |
| main.cc | command line, timing, statistics |

**Path tracing loop (`trace_path`).** Starting from a camera ray, repeat up to
`max_depth` times: find the closest surface the ray hits; if nothing is hit, add the
background light and stop; add the light emitted by the surface; choose a new
direction according to the material and multiply the path's *throughput* by the
fraction of light the surface reflects. Diffuse surfaces use cosine-weighted
random directions, mirrors reflect perfectly, glass reflects or refracts with a
probability given by the Fresnel equations (Schlick's approximation). After a few
bounces, *Russian roulette* randomly stops dim paths and boosts the survivors so
that the result stays unbiased.

**BVH.** Testing every ray against every triangle would cost O(#triangles) per ray.
The BVH is a binary tree of bounding boxes: each node's box contains all triangles
below it. It is built by recursively splitting the triangles at the median along
the longest axis (leaves hold at most 4 triangles). A ray first tests a node's box
and skips the whole subtree if it misses, so a ray only tests O(log n) boxes and
a few triangles.

**Rendering (`render`).** For each pixel and each sample, a random generator is
seeded from (pixel index, sample index), a jittered camera ray is generated and
`trace_path` is called; the pixel value is the average over samples.

## 4. How to build and run

Build and run from the repository root.

```sh
make -j
./pt -w 256 -h 256 -s 256 -S 1 -D 5 -o image.ppm
```

| option | meaning | default |
|---|---|---|
| -w, -h | image size | 256 x 256 |
| -s | samples per pixel | 16 |
| -d | max bounces | 8 |
| -S | scene id (0, 1, 2) | 0 |
| -D | mesh detail (20*4^D triangles per object) | 3 |
| -o | output PPM | image.ppm |
| -p | also write the linear float image (PFM) | none |
| -r | reference PFM; print RMSE against it | none |

The run above (61,452 triangles, 16.8M samples, about 60M rays) takes about 150 s
on one core. Work scales linearly with w * h * spp, and roughly logarithmically
with the number of triangles.

The program prints build/render time, number of rays and Mrays/s, the mean color,
a checksum of the image and, if requested, the RMSE.

## 5. How to verify the results

- **Visual:** the Cornell box shows the expected effects: color bleeding from the
  red/green walls, soft shadows, reflection in the mirror sphere, and a caustic
  under the glass sphere.
- **Furnace test:** `./pt -S 2 -D 3` prints `max |pixel - 1| = 0`.
- **Convergence:** render a reference with many samples (`-s 8192 -p ref.pfm`, 64x64)
  and compare: RMSE is 0.200, 0.095, 0.048, 0.023 for 16, 64, 256, 1024 spp, i.e. it
  halves when spp is multiplied by 4, as expected for an unbiased estimator.
- **Mesh vs. analytic spheres:** scene 1 with fine meshes converges to the same image
  as scene 0 (same mean color and same RMSE against the scene 0 reference).
- **Determinism:** every (pixel, sample) has its own random seed, so the image does
  not depend on the order in which samples are computed. The checksum must be
  identical between the serial and the parallel versions (with the same compiler
  and flags; e.g. fused multiply-add can change the last bits).

## 6. Parallelism and what to optimize

- **Pixels and samples are independent**: millions of independent tasks, suitable
  for multicore (OpenMP) and GPU (CUDA). No synchronization is needed except
  writing the result.
- **Load imbalance**: paths have different lengths (rays escaping through the open
  front stop after 1 bounce, rays in the glass sphere bounce many times), so static
  scheduling of rows can be unbalanced; dynamic scheduling or tiles help.
- **Memory access**: BVH traversal reads nodes and triangles in an irregular order;
  node layout, compact node/triangle formats and float instead of double affect
  cache behaviour.
- **SIMD**: test one ray against several boxes/triangles at once (wider BVH), or
  several rays at once (ray packets).
- **GPU**: threads in a warp diverge when their rays hit different materials or
  terminate at different depths; reorganizing the work by bounce ("wavefront path
  tracing") is a known remedy.
- **Algorithmic**: a better BVH (surface area heuristic) and explicit light sampling
  (next event estimation) reduce the work per ray and the noise per sample.
